01问题诊断：为什么之前导出总对不上

工具原有两条独立渲染链路：页面预览走 DOM+CSS，导出 PNG 走手写 Canvas 绘制器逐板块重绘。两套代码各维护一套字号、间距、圆角数值，且单位体系不同——预览是「窗口宽度百分比 + 固定 CSS px」，导出是「1242px 设计稿 + 硬编码 ×2.2 经验换算」。只有当窗口宽度恰好让预览列约 565px 时两者才碰巧一致；窗口一变，字号比例整体错位。这解释了你两轮反馈的同一类症状：换算出来的字永远和预览差一截，而且差多少随窗口变。

另有两个独立缺陷叠加：

  • 字体门禁缺失——原导出链路只等待「全局字体」，从不等标题字体/正文字体的 webfont 加载完成，在线字体（jsDelivr 上的 @fontsource 分包）慢或失败时，导出静默落入回退字体，这就是「字体现在还是有问题」的直接原因。
  • PSD 文字层坐标是硬编码近似值——与实际排版无关，PS 里打开位置对不上。

02方案对比与选型

「预览即所得」有三种主流架构，核心差异在预览和导出是否共享同一份渲染：

方案像素一致性PSD 分层兼容字体处理主要风险
A. 统一 DOM + 截图库（html2canvas / html-to-image）高（同源渲染）位图可做合成层，文字层需自行补依赖 document.fonts.ready，截图库自己处理字体html2canvas 对 box-shadow/zoom 支持差；需引第三方库
B. 统一 Canvas 渲染（预览即导出小样）理论最高原生兼容 ag-psdcanvas 绘制前必须显式等字体预览交互全部重写（选中/悬停/工具提示都要在 canvas 上自绘），工作量与回归风险最大
C. 手写双链路修补（本工具原状）永远存在漂移已兼容每侧各自处理每加一个板块要同步两套代码，这次修了下次还偏

选型结论

采用 方案 A 变体：保留 DOM 预览（交互零改动），导出改为「DOM 序列化 → SVG foreignObject → 位图化」，即 html-to-image 同款原理，但为工具定制内联实现（约 200 行，不引外部库）。同一份 DOM 既是预览也是导出源，一致性由结构保证而非数值对齐；原 Canvas 绘制器完整保留为 legacy 回退（导出脚本加载失败时自动降级）。方案 B 的一致性上限更高，但要重写全部预览交互，与「工具核心思路不变」的前提冲突，不取。

03最终架构

S1zoom 安全区导出前把预览临时重建为 zoom=1（设计宽度原尺寸）——CSS zoom 子树内 computed style 是缩放后值，直接克隆会得到缩小版布局；导出完恢复用户缩放。
S2字体门禁document.fonts.load 对标题/正文两种角色的 400/700/900 三档字重逐一就绪，再等 document.fonts.ready 全局稳定，才开始渲染导出。
S3资源内联SVG-as-Image 沙箱不加载 blob:/http 外链资源（html-to-image 转存 dataURL 的同款原因），img src 与 CSS background-image 全部转为 dataURL 后再序列化。
S4序列化位图化克隆预览节点 → 内联全部计算样式 → 包进 foreignObject → XMLSerializer → dataURL SVG → Image → canvas，按 doc.exportScale 倍率放大输出。
S5产物输出PNG 直接下载；连续长图对整条 strip 同流程；PSD 用 1x 位图做「合成预览」图层写入 ag-psd。

04基准校准：750 设计宽度与 ×2.08 系数

竖屏 H5 的行业惯例是 750×1334 设计宽度（iPhone 6/7/8 逻辑分辨率 ×2），二次元手游活动页、公众号长图均按此基准出稿；1242 是 Plus 系列物理宽，现已过时。你的诉求「回到我原本的预览视觉」换算如下：原预览在 46% 缩放下画布显示宽约 360px，你认可的字号比例 = DOM px ÷ 360；迁移到 750 设计宽度后，所有视觉值按 750 ÷ 360 = ×2.08 放大，导出再按 2x 倍率输出 1500px 宽成图——手机上阅读大小与原网页视觉一致。

05字体方案

在线字体走 @fontsource（jsDelivr CDN）按 unicode-range 分片加载，中文包只拉取命中的分片。导出门禁：导出前对标题字体、正文字体分别调 document.fonts.load(weight 24px family, 文本样本)（400/700/900 三档），Promise.all 汇聚后再等 document.fonts.ready，任何一档失败不阻塞导出但会保留回退栈，不再静默错位。预览与导出共用同一 font-family 栈（C.FONTS → fontStack()），三端字形一致。

已知边界：jsDelivr 在大陆存在间歇性慢/不可达。若某网络环境频繁回退，可将 banner-builder-constants.js 中 FONTS 的 css 数组换成 npmmirror 镜像（registry.npmmirror.com/@fontsource/...）或本地化字体文件，字段格式不变。PSD 里的文字层在 PS 打开时若本机未装对应字体会按 PS 规则回退显示——位图合成层不受影响，文字层的字体名已按角色写入。

已知边界：① PSD 为「合成位图 + 结构分组」形态，文字不以可编辑文字层输出（legacy 链路保留旧文字层形态可对照）；② backdrop-filter（glass 毛玻璃）位图化不支持，导出中弱化为半透明底；③ jsDelivr 弱网时门禁等待有短暂延迟，属字体就绪校验正常表现；④ 自研序列化兜底链路存在 box-sizing/flex 白名单缺口（本轮主因），仅作 html-to-image 不可用时的应急回退，输出可能有偏差——主链路优先保证 vendor 库可用（js/vendor/html-to-image.js 本地化，无外网依赖）。

维护要点：预览样式（tools/banner-builder.html 的 .bb-art-* 系列）与绘制器（banner-builder.js 的 paint* 函数族）已由 px2/styleCardPad/cardRadius 三个共用函数绑定，卡片级数值改一处即两侧同步；自由文本等独立字号仍需两侧同改，对照表见 04 节参数表。后续若新增板块模板，DOM 侧写渲染函数、Canvas legacy 侧补对应 paint 函数即可，新导出引擎自动继承 DOM 侧。
